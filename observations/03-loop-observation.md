# 3번 — 루프를 처음 돌려 본 관찰 (2026-09-12)

설계: `DESIGN.md` 4b·5·7절. 대상은 module-harness 자신이다 — DESIGN 5절이 "첫 소비자는 이 리포다"
라고 적은 그대로, kod-remastered 가 아니라 여기서 먼저 돌렸다.

> **범위**: 루프가 만든 커밋 다섯 건(`2569d96`·`322d1e6`·`1918279`·`017e504`·`686f8c1`)의
> scope → change → reconcile → commit 전 구간. `review` 는 뒤 세 건에서만 돌았다.

---

## 1. 종료 조건은 채워졌나

DESIGN 2절의 4b 조건: "이 리포 자신의 **게이트 수정** 한 건이 루프만으로 커밋까지 간다".

`322d1e6` 이 그것이다 — `module-gate.mjs` 에 `--review` 를 더한 커밋이고, R1(watch 에 `.mjs`)과
R2(계약 섹션)를 둘 다 건드렸다. scope 가 `MODULE.md` 를 내고, reconcile 이 0 FAIL 을 확인하고,
commit 이 `계약:` 줄을 요구해 받았다. 손으로 `git commit` 한 곳은 없다.

5절 조건("리뷰 지적이 전부 특정 불변식 ID 를 인용한다")은 `--review` 의 출력이 ID 로만 구성되므로
구조적으로 만족한다. 다만 **지적이 실제로 나온 적은 아직 없다** — 다섯 건 모두 통과였다.
리뷰가 무엇을 막는지는 아직 관찰되지 않았고, 그것은 다음 관찰의 몫이다.

## 2. 루프가 자기 첫 용도에 막혔다 — 가장 큰 발견

`322d1e6` 을 만들다 `reconcile` 이 이렇게 끝났다:

```
loop: 게이트가 바뀌었다 — 기준선은 그 규칙으로 잰 것이라 더는 참이 아니다. `abort` 후 다시 `scope`
```

loop I3 이 설계대로 동작한 것인데, **그 설계가 이 루프의 첫 용도를 막았다.** DESIGN 5절은
"게이트를 고치는 커밋은 매번 R1 과 R2 를 건드려서 루프가 실제로 일해야 하는 변경이 가장 자주
일어나는 곳" 이라고 적었다. 그런데 게이트를 고치면 게이트 해시가 달라지고, 달라지면 세션이 거부된다.
루프가 가장 필요한 자리에서 루프를 못 쓴다.

I3 이 지키려던 것을 다시 읽으니 "세션을 버린다" 가 아니라 **"옛 규칙으로 잰 기준선과 새 규칙의
판정으로 차집합을 내지 않는다"** 였다. 거부는 그 목적을 이루는 한 가지 방법일 뿐이고, 다시 재는
것도 같은 목적을 이룬다. `1918279` 에서 HEAD 의 임시 worktree를 떠 새 게이트로 재측정하게 고쳤다.

**이것이 불변식을 "판정 가능한 한 문장" 으로 적는 이유다.** I3 이 "기준선은 HEAD 와 해시에 묶인다"
로만 적혀 있었으면 재측정은 규칙 위반으로 보였을 것이다. 무엇을 지키려는지가 문장 안에 있어서,
수단을 바꾸고 목적을 지킬 수 있었다.

부작용: 재측정은 HEAD 만 본다. scope 시점에 이미 더러웠던 변경은 재측정 기준선에 안 들어가므로
신규로 **과보고**된다. 과소보고보다 낫다고 판단했고, 그 판단은 계약서 I3 에 적혀 있다.

## 3. 기준선이 한 번 무의미했다 — 정직하게 적어 둔다

`322d1e6` 을 만들 때는 아직 재측정이 없어서, 이미 변경이 다 쌓인 트리에서 `abort` 후 다시 `scope`
했다. 그러면 기준선이 "변경 후" 상태가 되어 차집합이 언제나 비고, reconcile 의 "신규 0건" 은
아무것도 말하지 못한다. 그 커밋의 `게이트: 0 FAIL 0 WARN (신규 0)` 트레일러에서 **신규 0 은
증거가 아니다** — 0 FAIL 만 증거다.

이런 일이 다시 일어나지 않게 하는 것은 규칙이 아니라 순서다: 고치기 전에 `scope` 한다.
루프는 그 순서를 `commit` 에서만 강제하고(계약을 안 연 경로를 거부한다), 기준선의 시점까지는
강제하지 못한다. `scope` 가 "작업 트리에 이미 변경 N건이 있다" 를 크게 찍는 이유다.

## 4. `--review` 가 처음 낸 것

`686f8c1` (설치 도구·CI) 에서:

```
review: 5개 파일 변경 → 봐야 할 불변식 1개
[테스트] 1건 — `npm test` 통과. 그것이 증거다
  harness  I6  어댑터 문구의 출처는 스키마 하나다 …
```

파일 다섯을 고쳤는데 봐야 할 불변식은 하나다. 이것이 "리뷰 범위는 diff 가 아니다" 의 실제 모습이고,
`.github/workflows/ci.yml`·`package.json`·`README.md` 는 어느 불변식도 근거로 인용하지 않는 파일이라
리뷰가 볼 것이 없다는 뜻이다. **계약이 비어 있는 것과 리뷰할 것이 없는 것을 이 출력은 구분하지
못한다** — 둘 다 "0건" 으로 보인다. 지금은 사람이 구분한다.

## 5. 커밋이 커졌다 — R1 의 대가가 실측됐다

루프가 만든 다섯 커밋의 크기: 9·6·3·3·7 파일. 계약서가 매번 함께 실리므로 코드만 담는 커밋은
하나도 없다. [규칙 충돌-1] 이 예고한 그대로이고, 이번에 스키마가 그것을 명문화했다
("계약 갱신은 코드 커밋과 같은 묶음이다").

메시지가 둘을 나누는 것은 실제로 읽힌다 — `계약:` 줄만 훑으면 이 세션이 계약을 어떻게 바꿔 왔는지가
다섯 줄로 나온다. 다만 `--contract` 는 사람이 쓰는 문장이라 **거짓을 적어도 아무도 못 잡는다.**
게이트가 "계약서를 고쳤나" 를 보고 루프가 "무엇을 고쳤다고 적었나" 를 받을 뿐, 둘이 같은지는 아무도
안 본다. 지금 이 하네스 전체에서 가장 크게 남은 구멍이다.
